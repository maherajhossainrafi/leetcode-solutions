> **Quick answer:** Loop through `nums` once with a hash set. For each number, `insert` it into the set: if `insert` reports it was already there (`.second` is `false`), return `true`. If the loop finishes, return `false`. Time `O(n)` on average, space `O(n)`. Sorting and comparing neighbors also works, in `O(n log n)`.

# Solution Walkthrough

## 1. Problem Title

**Contains Duplicate** (LeetCode 217, C++) · [Problem link](https://leetcode.com/problems/contains-duplicate/)

## 2. Problem Summary

**Given:** a list (array) of whole numbers called `nums`.
**Find:** `true` if any value shows up **at least twice**, and `false` if every value is different.

**Constraints (the numbers that decide which approaches are allowed):**
- The list has between 1 and 100,000 numbers (`1 <= nums.length <= 10^5`).
- Each number is between -1,000,000,000 and 1,000,000,000.

**Why the constraints matter:** comparing every pair of 100,000 numbers takes about 5,000,000,000 comparisons. A judge handles roughly 100,000,000 simple steps per second, so a pair-by-pair solution would run out of time. Every solution below is faster than that.

**Tiny worked example:**
- `[1, 2, 1]` → `true` (the number 1 appears twice)
- `[1, 2, 3]` → `false` (all different)

## 3. Intuition

**Picture 1: a coat-check room.** You hand over your numbers one at a time. Before hanging each one, the attendant tells you "new" or "already here." The first "already here" is your answer. The technical term is a **hash set**: a container that stores each value once and answers "is it in here?" in about one step on average.

**Picture 2: a line of people sorted by height.** If two people are exactly 170 cm, anyone standing between them must be at least 170 and at most 170, so they are 170 too. Equal values always form one unbroken block. The technical term is **contiguous** (touching, with no gaps). So after **sorting**, you only compare neighbors.

**The "aha":** you do not need to compare everything with everything. Either *remember what you have seen* (hash set) or *arrange the data so twins stand together* (sorting).

**Recall hook:** *"Ask first, then store"* (hash set) and *"sort, and twins stand together."*

## 4. Approaches

| # | Name | Core idea in one line | Rank |
|---|---|---|---|
| 1 | Hash set: `count`, then `insert` | Ask the set first, store after | 3 (Average) |
| 2 | Hash set with a single `insert` | `insert` reports "new or not" in one trip | 2 (Average) |
| 3 | Sort, then compare neighbors | Sorting makes equal values neighbors | 4 (Worst) |
| 4 | Hash set with `reserve` and range-`for` | Same hash idea, no rebuilds, no index | 1 (Best) |

**Approach 1 (`count`, then `insert`).** For each number, ask the set whether it is already there (`count` returns 1 or 0). If yes, return `true`. If no, store it. It works because the set holds only the *earlier* numbers when you ask. It breaks if you store before asking (the number finds itself) or if you split the work into "store all, then ask all."

**Approach 2 (single `insert`).** `insert` returns a receipt (a `pair`). Its `.second` is `true` when the value was new and `false` when it was already there. So `if(!a.second)` means "duplicate found." This is the **same core algorithm as approach 1**, with one hash operation per number instead of two. It breaks if you forget the `!` and return on the first (always new) number.

**Approach 3 (sort, then neighbors).** Sort the array ascending, then compare each number with the one after it. It works because equal values become contiguous. It breaks if the loop reads `nums[i+1]` past the end, or if `nums.size() - 1` is used on an empty vector (`size()` is unsigned, so `0 - 1` wraps around to a huge number). The constraints guarantee `n >= 1`, so it is safe here. It also rearranges the caller's array.

**Approach 4 (hash set with `reserve` and range-`for`).** The **same core algorithm as approach 2.** It adds `reserve` (build enough buckets up front so the set never rehashes mid-loop) and a range-based `for` (no index, so no off-by-one). It also never modifies the input.

## 6. Edge Cases

| Case | Why it is tricky | What happens | How the solutions handle it |
|---|---|---|---|
| One element, `[7]` | No pair exists | Returns `false` | The hash set never sees a repeat; the sort loop does not run (`size()-1` is 0) |
| All equal, `[5, 5, 5]` | Many duplicates at once | Returns `true` as soon as the first repeat appears | Early return |
| Duplicate not adjacent, `[1, 2, 1]` | Comparing neighbors on an *unsorted* list misses it | Returns `true` | The set remembers; sorting makes twins neighbors |
| Duplicate only at the end, `[1, 2, 3, 3]` | Must not return `false` just because the first numbers were new | Returns `true` | `return false;` sits after the loop, not inside it |
| No duplicates at maximum size | Worst case for time | Returns `false` | O(n) and O(n log n) both finish comfortably |
| Negative numbers, `[-1, -1]` | Sign mistakes in hand-made logic | Returns `true` | Only `==` and hashing are used, never arithmetic on values |
| Extreme values ±10⁹ | Overflow if you add or multiply | No overflow | Values fit in `int` (max about 2.1 billion), and we only compare and store them |
| Empty vector (not allowed here) | Unsigned `size() - 1` wraps around | Would run off the end in approach 3 | Not an issue because the constraints guarantee `n >= 1`; say the assumption out loud |

## 7. Implementations

*On LeetCode you do not need any `#include` lines or `using namespace std;`. The judge already includes most standard library headers (such as `vector`, `unordered_set` and `algorithm`), and its starter code already writes `vector<int>` without `std::`. If you run this code on your own computer, add them yourself.*

### Approach 1: Hash set, `count` then `insert`

*What to notice:* the question (`count`) comes **before** the store (`insert`).

```cpp
class Solution {
public:
    bool containsDuplicate(vector<int>& nums) {
        unordered_set<int> check;
        for(int i = 0 ; i<nums.size();i++)
        {
            if(check.count(nums[i]))
            {
                return true ;
            }
            check.insert(nums[i]);
        }
        return false;
    }
};
```

### Approach 2: Hash set, single `insert`

*What to notice:* `insert` stores the number **and** reports whether it was new, so one hash operation does both jobs.

```cpp
class Solution {
public:
    bool containsDuplicate(vector<int>& nums) {
        unordered_set<int> check;
        for(int i = 0 ; i<nums.size();i++)
        {
            auto a = check.insert(nums[i]);
            if(!a.second)
            {
                return true ;
            }
        }
        return false;
    }
};
```

### Approach 3: Sort + neighbors

*What to notice:* it sorts the caller's vector in place, and `nums.size() - 1` is safe only because the constraints guarantee at least one element.

```cpp
class Solution {
public:
    bool containsDuplicate(vector<int>& nums) {
        sort(nums.begin(), nums.end());
        for(int i=0;i<nums.size()-1;i++)
        {
            if(nums[i]==nums[i+1])
            {
                return true;
            }
        }
        return false;
    }
};
```

### Approach 4: Hash set with `reserve` and range-`for`

*What to notice:* it is the **same core algorithm as approach 2**. `reserve` prevents rehashing mid-loop, and the range-based `for` removes the index.

```cpp
class Solution {
public:
    bool containsDuplicate(vector<int>& nums) {
        unordered_set<int> seen;
        seen.reserve(nums.size());

        for (int x : nums) {
            if (!seen.insert(x).second) {
                return true;
            }
        }
        return false;
    }
};
```

## 8. Improvements

- **Memory vs. speed:** sorting uses almost no extra memory (about O(log n) of stack) but costs O(n log n). The hash set costs O(n) memory and gains O(n) average time. Name this trade-off out loud in an interview.
- **Do not change the caller's data:** sorting `nums` in place changes the caller's array. Sort a copy if that matters, or use the hash set.
- **Avoid the unsigned trap:** in approach 3, write the loop as `i + 1 < nums.size()` instead of `i < nums.size() - 1`. Both stop at the same place, and the first never subtracts.
- **`reserve` trade-off:** it helps most when there is no duplicate (the set fills completely). If the duplicate shows up near the start, you have paid for buckets you never used.
- **Related problems:** *219. Contains Duplicate II* (sliding window plus a set), *220. Contains Duplicate III*, *1. Two Sum* (hash map), *242. Valid Anagram* (counting), *287. Find the Duplicate Number* (uses O(1) extra space with a clever trick).
- **Transfer:** "have I seen this before?" is the heart of many problems. A hash set answers it in about one step, and sorting makes "seen before" mean "stands next to me."

## 9. Mistakes

| What goes wrong | Why | Fix | Lesson |
|---|---|---|---|
| Two loops: store all, then ask all | Storing and asking treated as separate phases | One loop: ask first, store after | The set must hold only earlier numbers when you ask |
| `insert` before `count` in the same loop | Wrong order inside the loop | `count` first, `insert` after | Asking right after storing always answers yes |
| `insert` placed inside the `if` | Mixed up which case stores | `insert` after the `if` | Match each case: "seen it" gives the answer, "new" stores |
| `return false;` inside the loop | "The first number is new" treated as "no number repeats" | `return false;` after the loop | "False" is a claim about everything, so wait until all checks are done |
| Asking outside the loop using `i` | Scope | Ask inside the loop | A variable lives only inside its braces |
| A `//` comment placed ahead of code on the same line, e.g. `nums=//{1,2,3,4,2,4}` | The comment swallows the rest of the line, leaving broken code | Keep examples on separate comment lines | A `//` comment hides everything after it on that line |
| `nums.size` without `()`; bare `return;` | Mistaking a function for a field; forgetting the return type | `nums.size()`; `return true;` / `return false;` | Functions need parentheses, and returns must match the return type |
| `check.count(...)` result thrown away | A returned value needs to be used | Put it in an `if` | A function's answer does nothing until you use it |
| Declaring the `pair` by hand, calling `first(...)` / `second(...)` with parentheses, a comma inside `if`, or calling `insert` twice | Not realizing `insert` returns the receipt | `auto a = check.insert(...)`, read `a.second` | Catch a returned value, and slots are read, not called |
| `if(a.second)` returning `true` (or swapping the returns to compensate) | Mixing up "new" with "duplicate" | `if(!a.second)` | Trace the first number of a tiny array |
| `class Solution` missing its closing `}` | Brace matching | One more `}` before the final `;` | Indent, then count the braces |

**Other common pitfalls:** inserting before asking in a hash set, forgetting the `!` on `.second`, and using `size() - 1` on an unsigned type.

## 10. Learnings

1. **"False" is a claim about everything.** Only say it after every check is done.
2. **Order inside a loop matters:** ask the set first, store after, or the number finds itself.
3. **Hash sets** trade O(n) memory for near-O(1) lookups, using buckets, a remainder rule, and short chains.
4. **`insert` returns a receipt (`pair`):** `.second` tells you whether the number was new, so one call replaces `count` plus `insert`.
5. **Sorting makes equal values contiguous**, so a neighbor check is enough.
6. **Brace discipline:** indent, then match every `{` to its `}`.
7. **Trace a tiny input by hand** before submitting code.

**Pattern rules of thumb:**
- If a problem says "any value appears twice," think hash set first, sorting second.
- If a loop body reads `i+1`, stop the loop one spot earlier, and avoid subtracting from `size()`.
- If you catch yourself writing `return false` inside a loop, stop and ask whether everything has been checked yet.
